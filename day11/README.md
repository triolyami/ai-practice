# Модель памяти агента: три слоя — день 11

Задание: описать и реализовать модель памяти для агента. Разделить
информацию минимум на 3 типа: краткосрочная (текущий диалог), рабочая
(данные текущей задачи), долговременная (профиль, решения, знания). Сделать
так, чтобы разные типы памяти хранились отдельно, явно выбирать, что и куда
сохраняется. Проверить: какие данные попадают в каждый слой, как это влияет
на ответы агента.

База — день 10 (Agent + SQLite-персистентность + подсчёт токенов +
пост-ходовой экстрактор памяти). Убраны все стратегии контекста
(`window/facts/branches`), форк и `facts.py`: модель памяти заменяет их —
`facts.py` вырос в `memory.py`.

## Три слоя — три разных хранилища

Слои различаются **областью жизни** (scope) и физически лежат в разных
местах:

```
запрос = [system: личность]
       + [system: ДОЛГОСРОЧНАЯ ПАМЯТЬ — memory/longterm.md]   если layers.longterm
       + [system: РАБОЧАЯ ПАМЯТЬ — цель/план/факты задачи]     если layers.working
       + вся история диалога (MAX_TURNS)                       если layers.short
       + [user: новое сообщение]
```

| слой | область / время жизни | хранилище | кто пишет |
|---|---|---|---|
| краткосрочная | этот чат | таблица `messages` | автоматически, каждое сообщение |
| рабочая | задача = область чатов | таблица `workspaces` (JSON) | LLM-экстрактор + пользователь |
| долговременная | пользователь, навсегда | файл `memory/longterm.md` | LLM-экстрактор + пользователь |

- **Краткосрочная** — полный транскрипт диалога, уходит в запрос как есть
  (окна нет — умерло вместе со стратегиями дня 10).
- **Рабочая** — карточка задачи `{goal, plan[], facts[[k,v]]}` в строке
  `workspaces`. Чат привязан к области (`sessions.workspace_id`); все чаты
  одной области делят одну рабочую память. Новый чат → личная область
  (id = session_id); «+» у заголовка области или поле в настройках
  привязывают чат к общей. Область переживает свои чаты: удалили диалоги —
  задача осталась и примет новый чат.
- **Долговременная** — markdown-файл с секциями `## Профиль / ## Решения /
  ## Знания` и строками `- ключ: значение`. Один на всех, вне базы —
  переживает сброс, удаление чатов и перезапуск; можно открыть и править
  руками хоть в редакторе.

## Маршрутизация: автомат + ручное

- **Экстрактор.** После каждого `done` агент одним non-stream вызовом
  (temperature 0) отдаёт модели текущее рабочее состояние + содержимое
  longterm + ещё не учтённые сообщения и получает обновлённое состояние в
  строгом текстовом формате (`ЦЕЛЬ: / ПЛАН: / ФАКТЫ: / ДОЛГОСРОЧНОЕ:`,
  секции `Профиль | ключ: значение`). Маршрутизация в промпте: рабочая —
  всё, что относится к текущей задаче; долговременная — только сведения о
  пользователе, которые переживут задачу И читаются без переписки
  (контр-пример в промпте: «налоги: патент удобнее» — удобнее для чего?);
  факты задачи в longterm не дублируются, «запомни» слой не меняет,
  сомнение → не писать. Страховка
  — `drop_task_leaks()`: строки longterm, чей ключ уже лежит в рабочих
  фактах (текущих или новых), выбрасываются детерминированно.
  Парсер терпим к буллетам и мусору,
  лимиты: ≤15 фактов, ≤10 шагов, ≤30 строк longterm, ≤4000/8000 символов.
  Сбой → `notice`, память не трогается, ретрай на следующем ходу. Прогресс —
  `covered` в строке области, **по сессиям**: чат, присоединённый к чужой
  области, догоняет своей историей общее состояние (чанки по 12 сообщений).
- **Руки.** Панель «слои памяти» справа: долговременная — просмотр файла и
  редактирование целиком (`PUT /api/longterm`); рабочая — правка
  цели/плана/фактов (`PUT /api/working`) и кнопка «→ в долговременную» у
  каждого факта (`POST /api/promote`, переносит в секцию «Знания»);
  краткосрочная — счётчик сообщений (живёт только в чате). Область
  удаляется кнопкой «×» на её заголовке (`POST /api/workspace/delete`):
  память стирается, чаты возвращаются к личной.
- **Тумблеры слоёв** (`layers: {short, working, longterm}` в `config`) —
  для демонстрации «как влияет на ответы»: выключенный слой просто не
  попадает в запрос; `meta.layers` фиксирует, что было включено, а
  `meta.tokens.{longterm,working,history}` — цену каждого слоя.

## Файлы

- **`memory.py`** (наследник `facts.py`) — `update_memory()` (промпт
  «редактор памяти», критерий: данные задачи → рабочая, данные пользователя
  и общие знания → долговременная) + `drop_task_leaks()` (детерминированный
  фильтр задачных ключей в longterm), `parse_memory()`,
  `render_working/longterm_message()`, `read_longterm()` /
  `write_longterm()` (дедуп по ключу, в `applied` попадают только реальные
  записи — переписывание тем же значением не считается добавлением,
  перезапись файла целиком, под `MEMORY_LOCK`), `normalize_working()`.
- **`storage.py`** — + таблица `workspaces(workspace_id PK, name, state
  JSON, covered JSON {session_id: int}, updated_at)`, колонка
  `sessions.workspace_id`; `save/load/list/delete_workspace`,
  `set_session_workspace`, `drop_covered`; личная область чата
  автосоздаётся при сохранении.
- **`agent.py`** — `layers` + `workspace_id` в конфиге/снапшоте;
  `_request()` собирает слои; `_update_memory()` после `done` (событие
  `memory`); `promote(key)`; `reset`/`forget` чистят только запись `covered`
  этого чата — общее состояние не тронуто.
- **`server.py`** — порт **7870**; `parse_config` += `workspace` (≤120,
  имя → slug `ws-*`), `layers` (3 bool); эндпоинты `GET/PUT /api/longterm`,
  `GET /api/workspaces`, `PUT /api/working`, `POST /api/promote`,
  `POST /api/workspace/delete`; `/api/fork` и стратегия убраны.
  Конкурентность: глобальный BUSY → 409 на любой ход (общие хранилища
  делают параллельные ходы гонкой записи — дешевле сериализовать);
  `MEMORY_LOCK` страхует правки во время экстракции.
- **`tokens.py`** — `breakdown()` по 5 сегментам: system / longterm /
  working / history / request.

## Фронтенд

Копия дня 10 (dev-порт **5182**, прокси на 7870, localStorage `day11-*-v1`,
`dist/` собран и закоммичен):

- **«слои памяти»** справа — три секции: файл longterm (просмотр/правка),
  рабочая область (цель/план/факты, правка, «→ в долговременную» у факта,
  счётчик учтённых сообщений), краткосрочная (число сообщений диалога);
- **список чатов** сгруппирован по областям: заголовок области с «+»
  (новый чат сразу в ней) и «×» (удалить область); чаты без области — под
  «личная память»;
- **настройки**: имя/промпт/модель + поле «рабочая область» (datalist
  существующих) + три чекбокса слоёв; стратегии/окно убраны;
- **карта контекста**: 5 сегментов, «следующий запрос» показывает слои и
  область; панель токенов — две строки: «чат» и «обновление памяти»;
- мета под ответом: слои · область · контекст% · стоимость;
- в окно между `done` и `memory`-событием (пост-ходовой вызов экстрактора,
  ~2–5 с) у секций «долговременная»/«рабочая» крутится «обновляю…»;
- переключение чатов мгновенное: транскрипт и `agentInfo` кешируются в
  памяти (`transcriptCache`), `GET /api/agent` догоняет фоном; «загружаю
  диалог…» остаётся только для первого визита к чату без кеша.

## Сценарий «как слои влияют на ответы» (прогоняется вручную)

1. Скажите о себе что-то профильное («я — бэкендер на Python, в команде
   4 человека»), дождитесь `memory`-события → строки появятся в
   долговременной памяти.
2. Спросите «напиши сервис авторизации» с включённой долговременной — и
   тот же вопрос с выключенной (чекбокс в настройках): сравните ответы и
   `meta.tokens.longterm` / `meta.layers`.
3. Два чата в одной области: в первом обсудите задачу, во втором
   продолжите без повторения контекста — рабочая память общая. Третий чат
   в другой области её не видит.
4. Поправьте цель руками → следующий ответ учитывает правку; перенесите
   факт «→ в долговременную» → он появляется уже во всех чатах.
5. Сбросьте диалог («сбросить диалог»): краткосрочная чистится, рабочая и
   долговременная остаются.

Выводы сознательно не вшиты — прогон и наблюдения за вами.

## Принятые решения (и что отвергнуто)

- **Три разных хранилища**, а не одна таблица с колонкой «слой»: времена
  жизни разные (файл переживает даже удаление базы), и задание прямо
  требует «хранить отдельно». Отвергнуто: единый SQLite для всего
  (границу слоёв не видно) и всё-в-файлах (ломает конвенцию репозитория
  для сообщений).
- **Рабочая память — на область (workspace), не на чат**: сценарий «2
  чата — 1 задача» иначе не покрыть; личная область — вырожденный случай
  без лишней механики. Отвергнуто: per-chat working и один глобальный
  scratchpad (параллельные задачи мешали бы друг другу).
- **Запись памяти — пост-ходовым вызовом**, а не tool-calls в середине
  генерации: записи видимы (`memory`-событие, панель), провайдеро-
  независимо, не удлиняет time-to-first-token. Формат ответа — секции
  текста, не `response_format` (те же причины, что в дне 10).
- **`covered` — по сессиям внутри строки области**: у каждого чата свой
  курсор «сколько его истории уже учтено» → присоединение чужого чата к
  области догоняет его бэклог, reset/forget не ломает чужие курсоры.
- **Граница слоёв — по времени жизни данных, не по формулировке**: правило
  в промпте («переживёт ли строка закрытие задачи») + детерминированный
  фильтр `drop_task_leaks`. Отвергнуто: доверять разметке секций модели
  как есть — deepseek-v4-flash копировал задачные факты («дедлайн»,
  «проект») в ДОЛГОСРОЧНОЕ на каждом ходу; теперь такие строки режутся по
  совпадению ключа с рабочими фактами, а «→ в долговременную» остаётся
  ручным способом перенести факт осознанно.
- **Глобальный BUSY вместо per-session**: общие хранилища (строка области,
  файл) делают параллельные ходы настоящей гонкой; сериализация дешевле
  гранулярных блокировок и ничего не стоит в одиночном демо.
- **`longterm.md` — маркдаун с фиксированными секциями**: читается/правится
  вне приложения, инъекция — «файл как есть»; «этот слой переживает всё»
  видно физически.
