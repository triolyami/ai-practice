# Композиция MCP-инструментов — день 19

Задание:

> Создайте несколько MCP-инструментов, например: search, summarize,
> saveToFile. Реализуйте пайплайн: первый инструмент получает данные,
> второй — обрабатывает, третий — сохраняет результат. Проверьте:
> автоматическое выполнение цепочки; корректность передачи данных между
> инструментами. Результат: автоматический пайплайн из нескольких
> MCP-инструментов.

База — день 18 (агент с тулколлингом, MCP-хаб, чат-UI), но реестр
`MCP_SERVERS` сужен до одного сервера: демо-серверы дней 17/18
(`py-tools`, `ts-tools`, `tracker`, `scheduler`) убраны вместе с их
файлами, вотчером планировщика и закреплённым чатом «сводка» — модель
в чате видит только инструменты цепочки.
Ключевая мысль дня: **MCP-инструменты изолированы по построению —
инструмент не может вызвать другой инструмент**. «Пайплайн» поэтому
живёт не внутри инструментов, а в том, кто их вызывает: хост переносит
вывод одного вызова в аргументы следующего. День сравнивает три
оркестратора одной и той же цепочки.

## Три дорожки одного пайплайна

```
дорожка              оркестратор        данные между этапами        вердикт
-------------------  -----------------  --------------------------  ----------
1. модель в чате     agent loop         выход → контекст → модель    зависит:
                     (tool_calls)       заново печатает аргументы    от модели
2. код               POST /api/pipeline выход → переменная → args    exact
                                        (дословно, по построению)
3. композитный       внутри сервера     хопов нет — один вызов       n/a
   run_pipeline                         (контроль: это НЕ композиция)
```

Проверка «корректности передачи» — по хешам: у каждого вызова в трассе
`meta.tool_calls` теперь лежат `result_len` и `result_sha256` полного
результата (preview по-прежнему обрезанный) плюс `hop_exact` — совпал ли
строковый аргумент `text` этого вызова с результатом предыдущего.
В кодовой дорожке exact гарантирован построением; в дорожке модели —
честное измерение того, что модель реально отправила.

## Сервер pipeline (stdio, 4 инструмента)

| инструмент | параметры | что делает |
|---|---|---|
| `search` | `query`, `limit?` | абзацы `corpus/*.txt`, где встречаются ВСЕ термины запроса (слова ≥3 букв) |
| `summarize` | `text` | дайджест через deepseek-v4-flash, без ключа — экстрактивный фолбэк |
| `save_to_file` | `name`, `text` | пишет `out/<name>.txt` (имя санитизируется), вернуть путь и байты |
| `run_pipeline` | `query` | вся цепочка внутри одного вызова + дайджест этапов — контрольная дорожка |

`summarize` — инструмент, который сам ходит в LLM: ленивый клиент
строится на первом вызове (SDK падает на пустом api_key уже при
конструировании — тот же готча, что в дне 3). Нативные рассуждения
deepseek съедают `max_tokens` — бюджет 1400, иначе `content` приходит
пустым и срабатывал бы фолбэк.

## Дорожка 2: `POST /api/pipeline`

`{query, name?}` → три последовательных `HUB.call_tool` в потоке запроса
(ThreadingHTTPServer), NDJSON-стрим:

```
{"event":"start","lane":"code","query":"…"}
{"event":"stage","i":0,"tool":"search","input":{…},"output":"…","hop_exact":null,"sha256":"…"}
{"event":"stage","i":1,"tool":"summarize","input":{…},"output":"…","hop_exact":true,…}
{"event":"stage","i":2,"tool":"save_to_file","input":{…},"output":"…","hop_exact":true,…}
{"event":"done","ok":true,"verdict":"exact","result":"сохранено: out/x.txt (N байт)"}
```

Этап упал → следующие не вызываются, `done {ok:false, failed_stage}`.
Логика в генераторе `iter_pipeline(query, name, call_fn)` — точка
подмены для офлайн-проверки. Ходит под общим busy-lock: хаб зовёт
разделяемые stdio-сессии, параллельно с ходом чата им лучше не
пересекаться.

## Что показал живой прогон (deepseek-v4-flash)

- **Дорожка 1, явный промпт** («вызови по очереди … не переписывай
  текст»): модель сама собрала цепочку search → summarize →
  save_to_file за один ход, оба хопа `hop_exact=True` — данные прошли
  байт-в-байт.
- **Дорожка 1, естественный промпт** («найди, сожми, сохрани»): модель
  нашла короткий путь — вызвала композитный `run_pipeline` одним
  вызовом, а в `save_to_file` отправила уже свой пересказ →
  `hop_exact=False` («модель переписала данные»). Инструменты
  изолированы, но модель видит весь реестр и выбирает дешёвый
  инструмент — наглядное отличие «автоматической» дорожки от
  детерминированной.
- **Мёртвый сервер**: при убитом процессе pipeline модель честно
  перебирала альтернативы (run_pipeline, прямой summarize, чужие
  инструменты из тогда ещё полного реестра) вместо падения хода;
  кодовая дорожка на том же состоянии даёт `stage` с ошибкой и
  `done.ok=false` без зависания.

## Фронтенд

(dev-порт **5188**, прокси → 7876, localStorage `day19-*-v1`, `dist/`
закоммичен.)

- Панель «пайплайн дня 19» в правой колонке: запрос, имя файла,
  «запустить пайплайн» (дорожка 2 со стримингом этапов), «композитный»
  (дорожка 3 одним вызовом), кнопка «дорожка модели → в чат»
  подставляет проверенный промпт в поле ввода.
- У этапов — бейджи «хоп дословно» / «хоп изменён», итоговый вердикт
  exact / differs / n/a.
- В чате у фаз tool_call тот же бейдж из `meta.tool_calls` —
  «хоп дословно» / «модель переписала данные», переживает перезагрузку.

## Проверено

- `day19/offline_check.py` — без сети: цикл инструментов агента плюс
  in-process прогон pipeline-инструментов (поиск по корпусу,
  санитизация имени, композитный вызов), экстрактивный фолбэк
  summarize, `iter_pipeline` — порядок этапов, дословный пайпинг,
  verdict exact, обрыв на ошибочном этапе; `hop_exact` в
  `meta.tool_calls` — true/false/null.
- Живой прогон (выше): все три дорожки, сохранённые файлы в `out/`,
  мёртвый сервер — честные ошибки на обеих дорожках.

## Принятые решения (и что отвергнуто)

- **Три оркестратора вместо одного**: задание просит «проверить
  автоматическое выполнение и передачу данных» — оба свойства есть
  смысл только в сравнении. LLM-дорожка гибкая, но передаёт данные
  через контекст (lossy by design); кодовая — байт-в-байт; композитная
  показывает границу: «композиция» внутри сервера не композиция вовсе,
  хопов на уровне MCP нет.
- **Fidelity через хеши в трассе**, а не хранение полных результатов:
  `result_sha256`/`result_len`/`hop_exact` — ~10 строк в agent.py,
  работают на восстановленных транскриптах, meta не раздувается.
  Отвергнуто: эхо-хеши внутри инструментов (привязывало бы инструменты
  к эксперименту) и полный result в meta (жирно).
- **`summarize` внутри MCP-инструмента ходит в LLM** — бонусная
  находка «инструмент может быть умным»; фолбэк держит офлайн.
  Отвергнуто: чисто экстрактивный summarize — проще, но теряется
  находка; сеть нужна только для живого llm-режима.
- **Один сервер на все три инструмента**, а не по серверу на этап:
  неймспейсинг `srv__tool` доказан в дне 17, распыление ничего не
  добавило бы. Композитный `run_pipeline` оставлен — как контроль и
  потому что модель реально его предпочла.
- **Корпус — коммиченные тексты в `corpus/`**, не веб-поиск:
  детерминированно, офлайн, проверяемо. `out/` гитигнорится —
  генерируемый вывод.
