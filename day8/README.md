# Токены — день 8

Задание: добавить в код агента подсчёт токенов — для текущего запроса, для всей
истории диалога и для ответа модели; сравнить короткий диалог, длинный диалог и
диалог, который превышает лимит модели; показать, как растут токены и стоимость
по мере диалога и что ломается при переполнении. База — агент дня 6, теперь он
считает токены и сам объясняет своё поведение числами.

## Что добавлено к агенту дня 6

- **`tokens.py`** (новый) — эвристический счётчик на stdlib: оценка текста до
  отправки, разбивка запроса на «система / история / текущий запрос» и
  `trim_to_fit()` — отбрасывание старейших реплик, пока диалог не влезет в
  контекст.
- **`agent.py`** — перед каждым запросом агент оценивает промпт и сравнивает с
  лимитом контекста модели; после ответа собирает в `meta` точные числа от API
  (`prompt_tokens`/`completion_tokens`, как и в день 6), погрешность своей
  оценки, стоимость хода и накопительные итоги. У агента появились `totals`
  (суммарные токены и `$` за диалог), `token_log` (строка на ход) и параметр
  `overflow` — что делать при переполнении (см. ниже).
- **`config.py`** — у каждой модели прописаны `context_limit` и цены
  `price_in`/`price_out` (USD за 1M токенов).
- **`server.py`** — порт 7867, тело запроса до 4 МБ (через UI можно прислать
  ~600 000 символов), в `config` добавлен `overflow`.
- **`frontend/`** — панель токенов над чатом (гейдж «контекст занят»,
  накопительные токены и стоимость, столбики промпт-токенов по ходам),
  расширенная строка метаданных под каждым ответом, кнопки «длинный текст»
  (+10К/+50К/+600К символов) и переключатель режима переполнения в настройках.

## Как считаются токены

Три числа на каждый ход, два источника:

1. **Оценка до отправки** (эвристика, без зависимостей): кириллица ≈ 3.5
   символа/токен, остальное ≈ 4 символа/токен, +4 токена служебного оверхеда
   на сообщение. Разбивка: `system` + `history` + `request` = оценка промпта.
2. **Точные числа после ответа** — `usage` от провайдера (в день 6 уже
   приходил с `stream_options.include_usage`, теперь не просто отображается, а
   сверяется с оценкой и копится в итоги).

Точность эвристики видна под каждым ответом как «ошибка оценки +N%»: знак и
величина показывают, насколько локальная прикидка промахнулась для этой модели.
На коротких репликах ошибка больше (оверхед и округление), на длинных текстах —
меньше. Замер на реальных запросах к `deepseek-v4-flash`: на коротких ходах
оценка занижала на 33–42% — `prompt_tokens` у thinking-моделей включает
служебный шаблон рассуждения, которого в наших сообщениях нет; для glm-4.6
(рассуждения выключены) расхождение меньше. Для оценки длины диалога это не
мешает, а запас 8192 токенов на ответ покрывает её с запасом. Эвристика нужна
для одного: предупредить о переполнении **до** того, как платить за запрос.

Стоимость хода = `prompt_tokens × price_in + completion_tokens × price_out`.
Для DeepSeek взяты off-peak-цены (в peak-часы, 01:00–04:00 и 06:00–10:00 UTC
пн–пт, они вдвое выше), кэш-попадания не учитываются — это грубая оценка «по
прайсу», а не биллинг.

Лимиты и цены (`config.py`):

| модель | контекст | $ за 1M вход / выход |
| --- | --- | --- |
| `deepseek-v4-flash` | 1M | 0.15 / 0.60 (off-peak) |
| `deepseek-v4-pro` | 1M | 0.66 / 1.98 (off-peak) |
| `glm-4.6` | 200K | 0.60 / 2.20 |
| `glm-5.3` | 1M | 1.40 / 4.40 |

## Как растут токены и стоимость

Ключевое свойство чат-протокола: **история пересылается целиком с каждым
запросом**. Ход сам по себе может быть маленьким, но промпт растёт как снежный
ком: N-й ход тащит на себе все N−1 предыдущих. Поэтому суммарные
промпт-токены за диалог растут квадратично, а стоимость — быстрее линейной:
пять коротких ходов по 100 токенов ответа стоят не «5 × ответ», а
100 + 300 + 500 + 700 + 900 токенов промпта по нарастающей.

Где это видно в интерфейсе:

- панель над чатом — гейдж занятости контекста, суммарные токены и `$`,
  столбики «промпт-токены по ходам» (каждый следующий столбик выше предыдущего
  ровно на размер новой реплики);
- под каждым ответом — `промпт N · ответ M · история ≈H · запрос ≈Q ·
  контекст P% · $c`;
- `GET /api/agent?session_id=` возвращает `totals` и `token_log` за весь диалог.

## Переполнение контекста

Переключатель в настройках агента, два режима:

- **«ошибка»** (по умолчанию) — если оценка промпта + 8192 токена запаса на
  ответ превышает `context_limit`, агент **не отправляет запрос вообще** и
  объясняет, что не влезло: «оценка 342 907 токенов (система 29 + история
  171 441 + запрос 171 432), лимит модели 200 000 токенов». Ниже это и есть
  ответ на вопрос «что ломается»: без этой проверки ломался бы сам запрос —
  API вернул бы 400 «maximum context length», уже после того как диалог
  накопился; локальная проверка ловит переполнение до списания денег.
- **«обрезать историю»** (`trim`) — агент выбрасывает старейшие пары
  user/assistant, пока оценка не влезет в лимит (минус 8192 на ответ), и
  продолжает диалог. Под ответом появляется жёлтая пометка «агент забыл N
  реплик». Это самое наглядное влияние токенов на поведение: агент не падает,
  но теряет память — спросите то, что говорили в начале диалога.

Если не влезает даже пустая история (одно сообщение больше контекста) — режим
trim тоже вернёт ошибку.

### Как воспроизвести (самый дешёвый сценарий)

1. Возьмите модель **`glm-4.6`** (лимит 200K — до него проще всего дойти).
2. Кнопкой «+600К» вставьте длинный текст и отправьте — ход займёт ≈85%
   контекста (гейдж станет жёлтым), ответ обойдётся примерно в $0.12–0.15.
3. Отправьте ещё одну «+600К»:
   - в режиме «ошибка» агент откажется слать запрос с полной разбивкой чисел —
     это «что ломается», но бесплатно;
   - в режиме «обрезать историю» агент забудет первую реплику и ответит —
     это «как токены меняют поведение».

Для моделей с лимитом 1M тот же сценарий потребует ≈5 ходов по 600К (~$0.5+
на deepseek-v4-flash, заметно дороже на glm-5.3) — или длинного живого диалога
кнопками «+10К»/«+50К». Скриптов для автопрогона переполнения в дне 8 нет
намеренно: это самый дорогой эксперимент курса, решение запускать его — за
вами.

## Проверено без расходов

Логика агента проверена офлайн, на фейковом клиенте (`Agent(client=...)`,
паттерн дня 6), 24/24: разбивка оценки, погрешность против точных `usage`,
стоимость и накопительные итоги, рост истории от хода к ходу, отказ запроса в
режиме «ошибка» (в API не уходит ни одного вызова), обрезка истории и пометка
«забыл N реплик» в режиме trim, валидация `configure(overflow=...)`, сброс
счётчиков через `reset()`, поведение при отсутствии `usage` в стриме.
Реальные запросы при отладке: два коротких («привет»), переполнение не
запускалось.

## Запуск

Фронтенд собран и закоммичен в `day8/frontend/dist/`, Node не нужен:

```bash
cp .env.example .env   # DEEPSEEK_API_KEY и/или GLM_API_KEY
.venv/bin/python day8/server.py
```

Открыть <http://127.0.0.1:7867> (в WSL2 — по eth0-IP). Провайдеры и модели те
же, что в дне 6. Отличия в маршрутах: `POST /api/chat` принимает
`config.overflow` (`"error"` | `"trim"`), `GET /api/agent` дополнительно
возвращает `totals`, `token_log`, `overflow`, `context_limit`.

Класс `Agent` по-прежнему работает без сервера:

```bash
cd day8 && ../.venv/bin/python -c "from agent import Agent; a = Agent(overflow='trim'); print(a.send('привет'))"
```

`MAX_CONTENT` поднят с 8000 до 600 000 символов, `MAX_TURNS` прежние (20
реплик): задание дня — увидеть, как токены растут и что происходит при
переполнении, поэтому искусственно зажимать диалог больше нельзя.

## Пересборка фронтенда

```bash
cd day8/frontend
npm install        # один раз
npm run build      # dist/ для сервера
npm run dev        # режим разработки: :5179, прокси /api → :7867
```
