# Планировщик и фоновые задачи — день 18

Задание:

> Сделайте MCP-инструмент с отложенным или периодическим выполнением.
>
> Пример:
>
> 👉 reminder
>
> 👉 периодический сбор данных
>
> 👉 регулярный summary
>
> Инструмент должен:
>
> 👉 сохранять данные (JSON / SQLite)
>
> 👉 выполняться по расписанию
>
> 👉 возвращать агрегированный результат
>
> Результат:
>
> Агент, который работает 24/7 и периодически выдаёт сводку

База — день 17 без изменений (агент с тулколлингом, MCP-хаб, три сервера,
чат-UI). День 18 добавляет четвёртый MCP-сервер `scheduler` и недостающее
направление: результаты фоновых задач **сами доходят до пользователя** —
покрыты обе ветки задания (`once`-напоминания и `interval`-сбор данных)
и «агент периодически выдаёт сводку» буквально: события приходят
сообщениями в закреплённый чат «сводка».

## Архитектура

```
server.py (ThreadingHTTPServer, порт 7875)
   │  POST /api/chat      → Agent.send_stream — NDJSON (как в дне 17)
   │  GET  /api/mcp       → hub.servers()
   │  POST /api/mcp/call  → hub.call_tool(...)
   │  GET  /api/agent     → транскрипт сессии (фронт поллит «сводку»)
   │
   │  watcher-поток (daemon): каждые WATCHER_POLL_S=15 с
   │     HUB.call_tool("scheduler", "pop_events") ──┐
   │     каждое событие → assistant-сообщение       │
   │     {meta.kind="scheduler"} в сессию «сводка»  │
   │     (ChatStore load→append→save под BUSY_LOCK) │
   ▼                                                │
mcp_hub.py — daemon-поток с asyncio-циклом           │
   │                                                │
   ├─ py-tools  stdio   tools_server.py             │
   ├─ ts-tools  stdio   ts-tools/server.ts          │
   ├─ tracker   stdio   tracker_server.py           │
   └─ scheduler stdio   scheduler_server.py ◄───────┘
         │  уведомления идут через сам MCP:
         │  события — обычный tool-результат (JSON)
         ▼
      scheduler.db (WAL): jobs / datapoints / events
      ticker-поток внутри процесса: каждые TICK_S=30 с
      исполняет due-задачи; стартовый проход ловит
      просроченные once-задачи (catch-up на рестарте)
```

Ход данных целиком остаётся внутри MCP-границы: хост никогда не открывает
`scheduler.db` — события приезжают как результат инструмента `pop_events`.

## Хранилище и тикер

SQLite `day18/data/scheduler.db` (WAL), все записи сериализованы локом
внутри процесса:

```sql
jobs(id, kind,          -- 'once' | 'interval'
     label,             -- текст напоминания / имя сбора
     next_run,          -- epoch следующего исполнения
     interval_s,        -- NULL у once
     status,            -- pending | fired | cancelled
     fired_at)
datapoints(id, ts, metric, value)
events(id, ts, kind,    -- 'reminder' | 'collect'
       text, delivered) -- очередь: delivered=0 пока вотчер не забрал
```

Тикер — daemon-поток: просыпается каждые `TICK_S` и исполняет все
`pending`-задачи с `next_run <= now`. `once` → `fired` + событие;
`interval` → datapoint-строки + событие + `next_run += interval_s`
(пропущенные за простой такты не догоняются — рестарт не даёт всплеска
старых точек). При старте процесса один проход сразу: просроченные
`once`-задачи срабатывают — персистентность видна, а не заявлена.

На пустой базе сидится один `interval`-job (`interval_s=120`): сбор
метрик трекера — `SELECT status, COUNT(*) FROM issues` по
`day18/data/tracker.db`, по одному datapoint на статус. Цифры живо двигаются,
когда в чате создают задачи. Если `tracker.db` нет/не читается —
фолбэк на `loadavg1` из `/proc/loadavg`. Метка посева — `PRAGMA
user_version`: отменённый сборщик не воскреснет при рестарте.

## Инструменты scheduler

| инструмент | параметры | что делает |
|---|---|---|
| `remind` | `text`, `in_minutes` | `once`-job; ответ — id + время срабатывания |
| `job_list` | — | задачи: вид, статус, `next_run` |
| `job_cancel` | `id` | pending → cancelled; неизвестный → ToolError |
| `summary` | `window_min=10` | per-metric count/min/max/avg + сработавшие напоминания в окне — считается по базе на чтении |
| `pop_events` | — | недоставленные события по порядку, помечает delivered (системный, для вотчера) |

`pop_events` помечает события доставленными при чтении — поллер видит
каждое ровно один раз, очередь переживает рестарт любой из сторон.

## Доставка: вотчер → чат «сводка»

Daemon-поток в `server.py` раз в `WATCHER_POLL_S` сливает очередь через
хаб и дописывает каждое событие как `{role:"assistant",
meta:{kind:"scheduler"}}` в фиксированную сессию `summary` («сводка»).
Формат — одна строка по-русски: `ЧЧ:ММ — напоминание сработало: «…»` или
`ЧЧ:ММ — метрики трекера: issues.open=3 · …`.

- Сессия создаётся с полями по умолчанию первым же событием; это обычная
  строка в `sessions`/`messages` — транскрипт, персистентность и
  восстановление работают без новых механизмов, а сам чат «сводка»
  является исторической записью выдач.
- Вся инъекция под `BUSY_LOCK` (`load→append→save`): ход пользователя
  никогда не перетирается событием. Пока ход в полёте, полл очередь даже
  не трогает — события ждут в базе, ничего не теряется.
- После записи закэшированный агент «сводки» выбрасывается из реестра —
  следующее обращение собирает его из базы уже с событиями.
- Ошибки хаба/сервера — строка в лог, поток живёт и повторит на
  следующем полле.

## Константы тайминга (демо-каденс, в одном месте)

| константа | где | значение |
|---|---|---|
| `TICK_S` | `scheduler_server.py` | 30 с — период тикера (задачи могут опоздать до тика) |
| `COLLECTOR_INTERVAL_S` | `scheduler_server.py` | 120 с — интервал сид-сборщика |
| `WATCHER_POLL_S` | `server.py` | 15 с — полл очереди событий |
| `SUMMARY_POLL_MS` | `frontend/src/lib/constants.js` | 15 с — полл транскрипта «сводки» |

## Встроенная ось сравнения

- **«отложенное» vs «периодическое»** — одна таблица `jobs`, два вида:
  напоминание (`remind`) против сборщика (сид-interval). Видно в
  `job_list` и в чате «сводка» рядом.
- **push vs pull**: та же сводка доступна по требованию инструментом
  `summary` («что собралось?») — push-вариант приходит сам в «сводку»,
  pull-вариант вызывает модель по запросу.

## Демо-сценарий

1. «Напомни через 1 минуту проверить сборку» → модель вызывает
   `scheduler__remind`, задача появляется в `jobs` (видно через
   `job_list` или `POST /api/mcp/call`).
2. Ничего не делать ~1–2 минуты: тикер исполняет напоминание и сид-сбор,
   вотчер кладёт оба события в «сводку» — в списке чатов на закреплённой
   строке появляется бейдж с числом, в транскрипте — сообщения.
3. «Что собралось? Покажи сводку за 10 минут» → модель вызывает
   `scheduler__summary` — тот же агрегат (count/min/max/avg по метрикам
   + сработавшие напоминания), но по запросу.
4. Рестарт `server.py`: просроченные `once` срабатывают стартовым
   проходом, недоставленные события доезжают первым поллом — очередь в
   SQLite ничего не теряет.

## Проверено

## Принятые решения (и что отвергнуто)

- **Тикер — поток внутри MCP-процесса** (паттерн `tracker_api` из дня
  17): хаб и так порождает процесс, отдельного жизненного цикла нет,
  сирот не остаётся. Отвергнут **системный cron**: на WSL он умирает
  вместе с дистрибутивом — реальный аптайм тот же, а «инструмент
  исполняется по расписанию» становится косвенным, плюс внешний
  install/cleanup.
- **Одна таблица `jobs` на обе ветки задания** — напоминание это
  `once`-job, сборщик — `interval`-job; один тикер обслуживает оба.
- **Доставка pull-through-MCP, инъекция на стороне хоста**: события —
  обычный tool-результат `pop_events`, хост базу планировщика не
  открывает; вотчер — daemon-поток в `server.py`. Отвергнуты: UI-тост
  (нет записи), настоящий ход агента на каждое событие (тратит токены
  на каждый тик и борется за BUSY), SSE/WebSocket (новый канал ради
  ~15-секундной демо-задержки).
- **Сводки детерминированные**, не модельные: текст события —
  форматирование по сохранённым строкам; модельный вариант был бы тем же
  текстом дороже. Инструмент `summary` — pull-форма тех же данных.
- **`pop_events` помечает delivered при чтении** — падение вотчера между
  drain и save теряет пачку; окно субсекундное, события
  информационные — принято вместо двухфазного ack-инструмента.
- **Честный «24/7»**: планировщик работает, пока работает `server.py`
  (тот же практический аптайм, что у cron на WSL); задачи и события в
  SQLite переживают рестарт, просроченные напоминания догоняются
  стартовым проходом.
