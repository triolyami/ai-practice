# Инварианты и ограничения состояния — день 14

Задание: добавить в ассистента инварианты, которые он не имеет права
нарушать. Примеры инвариантов: выбранная архитектура, принятые
технические решения, ограничения по стеку, бизнес-правила. Сделать так,
чтобы: инварианты хранились отдельно от диалога; ассистент явно учитывал
их в рассуждениях; ассистент отказывался предлагать решения, которые их
нарушают. Проверить: что происходит при конфликте запроса и инварианта;
как ассистент объясняет отказ.

База — день 12 (Agent + SQLite + файловое хранилище + привязка к чату).
**Убрано**: профили, долговременная память, экстрактор, пайплайны — вся
персонализация (таблицы `sessions.profile_id`/`covered`, `profiles.py`,
`memory.py`, `memory/`, `profiles/`, `/api/profile*`, `step_*`-события).
Вместо «как со мной работать» — **«что нельзя нарушать»**: инварианты.

Двойная защита из лекции: текст инвариантов идёт в промпт (модель
*должна* отказаться), а детерминированный линтер проверяет ответ
независимо от того, послушалась ли модель.

## Набор инвариантов = файл, привязка = к чату

Наборы — markdown-файлы `day14/invariants/<slug>.md`, по файлу на набор.
Грамматика — тот же секционный формат, что у профилей дня 12, плюс
секция машинных проверок `## Проверки`:

```markdown
# Android-клиент: Kotlin + MVI
## Контекст
- проект: Android-приложение, новый код
## Правила
- язык: только Kotlin, Java запрещена
- ui: Jetpack Compose, XML-вёрстка запрещена
- архитектура: MVI — однонаправленный поток state/intent
## Проверки                <- линтер, не для модели
- бан-код: (?i)\brxjava|rxkotlin|compositeDisposable\b
- бан-код: (?i)@Inject|dagger\.|hilt\.
- бан: (?i)добавьте зависимость.*(dagger|hilt)
```

- Привязка ручная, на чат (`sessions.invariant_id` + `sessions.enforce`):
  чип «инварианты: X ▾» в композере, «без инвариантов» — пустая привязка.
- Файл читается **с диска на каждый запрос** — правка (из UI или снаружи)
  видна со следующего ответа; удалённый файл деградирует честно: блок не
  уходит, в мете `invariant_missing`.
- Лимиты: ≤30 строк на секцию, ≤200 символов на значение, ≤20 КБ файл,
  ≤20 проверок, ≤400 символов на паттерн, ≤120 символов имя.

## Линтер: два скоупа, протокол отказа

`lint_reply(text, checks)` — детерминированная проверка готового ответа:

- `бан` — regex по **всему тексту** ответа (для бизнес-правил:
  «доставка по Санкт-Петербургу» запрещена и в прозе);
- `бан-код` — regex только по **fenced-блокам** кода, включая языковой
  тег (для стека: упоминание RxJava в обсуждении — ок, в коде — нарушение);
- ответ, начинающийся с `ОТКАЗ`, **не линтится** — отказ обязан называть
  запрещённое («ОТКАЗ: RxJava запрещён инвариантом…»), иначе отказ сам
  падал бы на собственных проверках;
- битый regex помечается `broken` и пропускается — ошибка в файле набора
  не должна ронять чат.

Протокол отказа — строковый, детерминированный: инвариант-блок в промпте
обязывает модель при конфликте начинать ответ с «ОТКАЗ:», назвать
нарушенный инвариант и предложить ближайшую разрешённую альтернативу.
UI рисует бейдж «отказ».

## Три режима принуждения (`config.enforce`)

| режим | блок в промпте | линтер | нарушение |
|---|---|---|---|
| `выкл` (off) | нет | спит | не видно — базовая линия |
| `промпт` (prompt) | да | да | ответ коммитится, бейдж «нарушение» + список проверок в мете |
| `жёсткий` (enforce) | да | да | ответ стримится и помечается заблокированным → один ретрай с указанием сработавших проверок → повторное нарушение = синтезированный `ОТКАЗ` сервера |

- В enforce нарушенный ответ **стримится и потом блокируется** — это
  осознанно: пользователь видит, что именно собиралась сказать модель.
  В историю попадает только финальный ответ; заблокированные попытки
  хранятся в мете хода (`blocked_attempts`), не в контексте.
- Ретрай — один. Запрос повторяется с дополнительным system-сообщением
  «ЛИНТЕР: сработали проверки X»; история при этом не трогается (модель
  не видит свой отклонённый ответ — только разбор нарушений).
- Второе нарушение → сервер сам пишет `ОТКАЗ: ответ дважды нарушил…` —
  гарантированный отказ, даже если модель упорствует. Мета:
  `synthesized`, `attempts=2`, обе попытки в `blocked_attempts`.

## Состав запроса

```
запрос = [system: личность агента]
       + [system: ИНВАРИАНТЫ «имя» — правила + машинные проверки + протокол ОТКАЗ]   привязан + режим != выкл
       + [system: ЛИНТЕР — сработавшие проверки]                                    только в ретрае
       + вся история диалога (MAX_TURNS)                                            layers.short
       + [user: новое сообщение]
```

Блок инвариантов стоит после персоны и до истории: при конфликте с
промптом агента инварианты важнее — и это видно в карте контекста
(сегмент «инварианты») и в мете (`tokens.invariants`).

## Файлы

- **`invariants.py`** — файловое хранилище: `list_invariants()`,
  `read_invariant(slug)` (парсит при каждом чтении — кеша нет),
  `write_invariant`, `delete_invariant`, `slugify(name)`;
  `parse_invariant()` — секции + компиляция проверок;
  `lint_reply()`, `render_invariants_message()`, `synthesized_refusal()`,
  `format_violation_list()`.
- **`agent.py`** — `invariant_id` + `enforce` в `configure`/снапшоте;
  `_request()` вставляет инвариант-блок после персоны; `_run_single`
  держит цикл enforce (стрим → линт → violation-событие → ретрай →
  синтез отказа); память и профили удалены целиком.
- **`storage.py`** — `sessions.invariant_id` + `sessions.enforce`
  (привязка и режим переживают рестарт).
- **`server.py`** — порт **7872**; `config.invariant` (slug/пусто,
  `config.profile` → 400 с подсказкой) + `config.enforce`
  (off|prompt|enforce); `GET /api/invariants`, `GET /api/invariant?id=`,
  `PUT /api/invariant {id?,name,content}`, `POST /api/invariant/delete`;
  NDJSON: `start.meta.{invariant,enforce}` + событие `violation`
  (content + сработавшие проверки) на заблокированных попытках.
  Глобальный BUSY → 409.
- **`tokens.py`** — `breakdown()`: system / **invariants** / history /
  request.

## Сценарий «конфликт запроса и инварианта» (прогоняется вручную)

1. Привяжите `android-mvi`, режим «промпт», отправьте пробу «конфликт:
   RxJava» — модель обычно отвечает «ОТКАЗ: …» с альтернативой на Flow;
   если проскочит код на RxJava — бейдж «нарушение» и детали в мете.
2. Тот же запрос в режиме «жёсткий»: нарушение стримится и сворачивается
   в «попытка 1 — заблокирована», поверх стримится ретрай; упёртая модель
   получает синтезированный отказ сервера.
3. Проба «дискуссия: RxJava» — отказа быть не должно: обсуждение
   запрещённого разрешено протоколом, `бан-код` смотрит только в код.
4. Режим «выкл» при той же привязке — модель спокойно пишет RxJava:
   базовая линия без защиты, бейдж «линтер выкл».
5. Привяжите `dostavka-msk`, проба «конфликт: город» — бизнес-правило
   ловится «бан»-ом по всей прозе, не только кодом.
6. Отредактируйте набор в панели справа (или файл руками) — следующий
   ответ уже по новой версии; удалите файл — чат продолжает без
   инвариантов, мета скажет «не найден».

## Принятые решения (и что отвергнуто)

- **Набор — файл, не строка в БД** (как профили дня 12): листинг
  каталога и есть список наборов; правится любым редактором; «отдельно
  от диалога» из задания читается буквально — файлы вне `chat_history.db`.
- **Проверки живут в том же файле**, что и человеко-читаемые правила:
  инвариант и его машинная граница — одна сущность; `## Проверки` пишет
  владелец набора. Отвергнуто: отдельный `*.rules`/`*.yaml` рядом
  (расходятся две версии одного правила) и секция внутри `## Правила`
  (смешивает «для модели» и «для линтера»).
- **Два скоупа линтера**, а не один «бан по всему»: дискуссия про
  запрещённое легальна, код — нет. Один скоуп либо запрещает упоминания
  (ломает разговор), либо пропускает нарушения в прозе.
- **Линтер — regex, не LLM-судья**: детерминизм — весь смысл второй
  линии защиты; судья сам бы ошибался и стоил вызов. Regex груб (ловит
  паттерн, не смысл) — поэтому «жёсткий» всё равно оставляет
  модели второй шанс через ретрай.
- **Отказ — строковый протокол «ОТКАЗ:»**, не структурный флаг: модель
  его видит и воспроизводит естественно; префикс освобождён от линта
  сознательно (отказ обязан называть запрещённое).
- **Enforce стримит нарушение до блокировки**: альтернатива «буферизовать
  и не показывать» прячет самое интересное — что модель нарушила после
  инструкции. Показать-и-заблокировать честнее и лучше для демо;
  заблокированное не попадает в историю, так что контекст не травится.
- **Один ретрай**: больше попыток — больше токенов и та же модель с той
  же инструкцией; второе нарушение означает «модель не справляется» →
  детерминированный отказ сервера надёжнее третьего шанса.
- **Нет пре-фильтра запроса**: задание просит наблюдать конфликт и
  объяснение отказа — входной запрос должен доходить до модели и линтера,
  иначе демонстрировать нечего.
- **Режим — свойство чата, не набора**: один и тот же набор в двух чатах
  даёт A/B промпт/жёсткий рядом; привязка и режим хранятся в `sessions`,
  как `profile_id` в дне 12.
