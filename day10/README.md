# Управление контекстом: три стратегии (без summary) — день 10

Задание: реализовать в агенте минимум три стратегии управления контекстом и
переключатель между ними — **Sliding Window** (только последние N сообщений),
**Sticky Facts / Key-Value Memory** (блок «ключ: значение» + последние N
сообщений) и **Branching** (чекпойнт → две независимые ветки от одного места).
Прогнать один и тот же сценарий на каждой стратегии и сравнить качество,
стабильность, расход токенов и удобство. Сценарий и прогон — вручную (как в
дне 9): день 10 делает сравнение возможным — переключатель стратегий в одном
диалоге, раздельные счётчики расхода и карта контекста.

База — день 9 (SQLite-персистентность + подсчёт токенов/стоимости), из него
убрано всё summary-хозяйство: `compressor.py` удалён, вместо него —
`facts.py`; режимы `off/rolling/chunks` заменены на `window/facts/branches`.

## Три стратегии

Полный транскрипт по-прежнему хранится целиком (в истории агента и в базе) —
стратегия меняет только то, что уходит в запрос:

```
window:    запрос = [system] + последние N сообщений + [новый вопрос]
           └── всё старше N модель не видит вообще, безвозвратно

facts:     запрос = [system] + [факты «ключ: значение»] + последние N сообщений + [вопрос]
           └── факты обновляет та же модель после каждого ответа

branches:  запрос = [system] + вся история + [вопрос]
           └── разгрузка не срезанием, а ветвлением: «⤵ ветка отсюда»
```

- **window** — ноль лишних вызовов: в `_request()` берётся `history[-N:]`,
  остальное считается как `outside` («за окном»). Дёшево, но деталь за окном
  теряется навсегда.
- **facts** — после каждого завершённого ответа агент вызывает модель
  (non-stream, temperature 0, та же модель, что и чат): старые факты +
  новые сообщения → обновлённый список строк «Ключ: значение» (≤15 фактов,
  парсер терпим к буллетам, значение обрезается до 200 символов). Сбой →
  событие `notice`, состояние не тронуто, ретрай на следующем ходу. При
  переключении другой стратегии на факты накопленный хвост догоняется за
  один вызов (чанки по 12 сообщений). Расход этих вызовов считается
  отдельно — бакет `facts_calls`.
- **branches** — история не режется; чекпойнт — это точка форка. Кнопка
  «⤵ ветка отсюда» у любого сообщения вызывает `POST /api/fork`:
  сервер создаёт **новый чат** с копией истории до этого сообщения (личность,
  модель, стратегия и накопленные факты наследуются, счётчики расхода — с
  нуля, честно по ветке). Две ветки от одного места = два форка одной точки;
  переключение — обычный список чатов слева. Родство хранится в базе
  (`parent_id`, `fork_len`) и переживает перезапуск сервера.

Размер окна N (2–50, по умолчанию 10) — один и тот же для window и facts,
настраивается в настройках агента. Стратегию можно переключать в любой
момент внутри диалога; счётчики промпт+ответ ведутся отдельно по каждой
стратегии, как в дне 9.

## Файлы

- **`facts.py`** (новый, вместо `compressor.py`) — `update_facts()`
  (промпт «редактор памяти диалога», строгий формат «Ключ: значение»,
  возвращает пары + usage + сырой текст), `parse_facts()` / `cap_pairs()`,
  `render_facts_message()` — блок фактов становится вторым системным
  сообщением запроса (тот же слот, что у сводки в дне 9).
- **`agent.py`** — `strategy` ∈ `window|facts|branches` вместо
  `compression`, `window_size` вместо `RECENT_KEEP/SUMMARY_EVERY`;
  `_update_facts()` после `done` (замена `_compress_history`), событие
  `facts` (замена `summary`), `notice` как в дне 9; `meta.strategy`,
  `tokens.extra` (вместо `tokens.summary`), `outside` (за окном / покрыто
  фактами / 0 у веток); `fork(count)` строит дочернего агента из
  снапшота с укороченной историей (факты наследуются, `covered`
  обрезается, бакеты totals обнуляются); `snapshot()`/`from_snapshot()`
  переносят стратегию, окно, факты и родство.
- **`server.py`** — порт **7869**; `parse_config` валидирует `strategy` и
  `window_size`; новый эндпоинт `POST /api/fork {session_id, count}` →
  `{ok, session_id, ...describe}` (под локом сессии: родитель в этот момент
  не должен генерировать); `/api/chat`, `/api/reset`, `/api/forget`,
  реестр LRU и сохранение по `done` — без изменений от дня 9.
- **`storage.py`** — таблица `sessions`: `strategy`, `window_size`,
  `facts_state` (JSON), `parent_id`, `fork_len`; `messages` не изменилась.
- **`tokens.py`** — как в дне 9, ключ `summary` → `extra`.
- **`config.py`** — как в дне 9 (модели, цены, лимиты контекста).

## Фронтенд

Копия дня 9 (dev-порт **5181**, прокси на 7869, localStorage `day10-*-v1`,
`dist/` собран и закоммичен):

- в настройках — сегех «стратегия контекста» (окно / факты / ветки) и
  поле «размер окна N» (скрывается для веток); чип в композере показывает
  активную стратегию и размер окна;
- у каждого сообщения при стратегии «ветки» — кнопка «⤵ ветка отсюда»
  (появляется при наведении): форк создаёт новый чат «… · ветка» с бейджем
  «↳ N» и сразу переключается на него;
- «карта контекста» справа: сегменты система / факты / сообщения / запрос,
  подпись под «следующим запросом» зависит от стратегии (за окном N ·
  факты покрывают N · вся история);
- панель «что помнит агент» → список фактов «ключ: значение» с числом
  учтённых сообщений (для window — честное «блока памяти нет», для веток —
  подсказка про форк);
- панель токенов: расход по трём стратегиям отдельными строками +
  строка «обновление фактов» (служебные вызовы стратегии facts).

## Сценарий для сравнения (прогоняется вручную)

Один и тот же сценарий «собираем ТЗ» (10–15 сообщений) на каждой стратегии:
в настройках выбрать стратегию, вести диалог, затем сменить стратегию и
продолжить в том же диалоге (счётчики по стратегиям раздельные) — или
завести по чату на стратегию. Для веток: дойти до чекпойнта, снять две
ветки от одного сообщения и развести их разными решениями.

Сравнивать:

1. **качество** — помнит ли агент цель/бюджет/решения на 10-м ходу;
2. **стабильность** — что происходит с деталями, которые вышли «за окно»
   (window) или попали/не попали в факты (facts);
3. **расход токенов** — панель «расход по стратегиям»: window режет промпт
   сильнее всех, facts платит за окно поменьше, но добавляет служебные
   вызовы обновления фактов, branches не экономит ничего, зато ничего
   не теряет;
4. **удобство** — window не требует ничего, facts показывает память
   явно (её можно прочитать), branches требует ручной работы с чекпойнтами.

Выводы сознательно не вшиты — прогон и наблюдения за вами.

## Принятые решения (и что отвергнуто)

- **Ветка = отдельный чат**, а не дерево сообщений внутри одной сессии:
  переиспользует механику дня 7 (персистентность, реестр, 409) почти без
  изменений; дерево потребовало бы новой схемы БД и перерисовки всего чата.
- **Факты обновляются после ответа**, а не до запроса: не удлиняет время до
  первого токена; обновление «до» переехало бы в критический путь каждого
  хода. Состояние после `done` сохраняется тем же механизмом «save после
  генератора», что и в дне 9.
- **Парс «Ключ: значение» вместо `response_format=json_object`**:
  провайдеро-независимо (deepseek и zai сразу), а для KV-списка JSON
  ничего не добавляет.
- Пустой список фактов — валидный результат («запоминать нечего»); а вот
  непустой ответ без единого «ключ: значение» считается сбоем формата —
  `notice` и ретрай, старые факты не затираются.
