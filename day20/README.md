# Оркестрация MCP — день 20

Задание:

> Зарегистрируйте несколько MCP-серверов. Сделайте так, чтобы агент
> выбирал нужный инструмент, корректно маршрутизировал запросы и
> выполнял длинный флоу взаимодействия. Проверьте: сценарий, в котором
> используются инструменты с разных серверов; корректность выбора и
> порядка вызовов. Результат: длинный флоу взаимодействия с несколькими
> MCP-серверами и инструментами.

База — день 19 (агент с тулколлингом, MCP-хаб, чат-UI), но реестр снова
расширен: день 19 сужал его до одного сервера, день 20 возвращает
несколько — и добавляет проверяемый сценарий. Ключевая мысль дня:
«маршрутизация» живёт на двух уровнях — **хаб** диспетчерует
`srv__tool` по префиксу (механика, доказана в дне 17), а **выбор**
инструмента и порядок делает **модель** по описаниям (семантика — это и
есть предмет проверки).

## Реестр: 4 сервера, все stdio

| сервер | инструменты | роль |
|---|---|---|
| pipeline | search, summarize, save_to_file, run_pipeline | корпус → дайджест → файл (из дня 19) |
| tracker | issue_list, issue_get, issue_create, issue_set_status, issue_comment | задачи в SQLite, REST внутри процесса (из дня 18) |
| scheduler | remind, job_list, job_cancel, summary, pop_events | напоминания + свой тикер (из дня 18) |
| py-tools | server_time, add, echo, notes_list, notes_add | **дистрактор**: notes_add семантически близок к задаче трекера — так «выбор нужного инструмента» проверяемо, а не предполагается |

ts-tools сознательно не в реестре: межъязыковой интероп доказан в дне
17, а node_modules ничего не добавляют к вопросу дня.

## Сценарий и проверка

`flow.py` держит сценарии: свободный промпт (`cross-server`) и тот же
флоу рецептом (`cross-server-explicit`, контрольная дорожка). Ожидания
— не полный порядок, а частичный: `expect` — подпоследовательность
только там, где порядок продиктован зависимостью данных (search →
summarize, issue_create → issue_comment — комментарию нужен id задачи);
`require` — шаги, которые должны случиться, но в любом месте (remind не
зависит от комментария). Плюс `min_servers` и `forbid` (дистракторы).

```
flow_run.py → POST /api/chat → NDJSON-стрим → meta.tool_calls
                                              │
                                              v
                              check(trace, spec) → вердикт по критериям:
                              order / require:* / servers /
                              no_distractors / no_errors + хопы
```

Хопы `hop_exact` (sha256 результата против text-аргумента следующего
вызова — из дня 19) показывают, где данные пересекли границу серверов
дословно, а где модель их переписала.

## Что показал живой прогон (deepseek-v4-flash)

- **Свободный промпт: PASS** — 8 вызовов, 4 сервера. Модель сама
  собрала search → summarize → issue_create → issue_comment → remind;
  попутно взяла `py-tools__server_time` (узнать время — легально, не
  дистрактор). Лишние разведывательные search'и трассе не мешают:
  проверяется подпоследовательность.
- **Рецепт: PASS** — 5 вызовов, учебниковый порядок, один хоп дословно.
  Разница дорожек: свободный промпт исследует (9 вызовов в первом
  прогоне), рецепт исполняет.
- **Найденный ложный FAIL**: первый прогон поставил `remind` ДО
  `issue_comment` — семантически верно (зависимости нет), но строгая
  полная подпоследовательность считала это ошибкой порядка. Так родился
  `require`: проверять порядок надо только там, где его вынуждают
  данные.
- **Хопы «переписано»**: модель добавляет к дайджесту префикс
  («Дайджест по материалам корпуса:…») — `hop_exact=False`. Данные
  доходят по смыслу, но не байт-в-байт: повтор дня 19 на границе
  серверов.
- `MAX_TOOL_ROUNDS` пришлось поднять 5 → 10: зависимые вызовы не
  батчатся, первый прогон потратил 9 раундов — старый лимит обрезал бы
  флоу посередине.

## Проверено

- `day20/offline_check.py` — без сети: весь набор дня 19 плюс
  `check()` на синтетических трассах (порядок, require, дистракторы,
  ошибки, переупорядочивание remind↔comment как легальный случай).
- Живой прогон обеих дорожек: PASS/PASS; заметки-дистрактор не тронуты;
  напоминания реально встали в очередь планировщика (job_list).

## Принятые решения (и что отвергнуто)

- **Частичный порядок вместо полного** — проверять надо зависимости,
  а не буквальную очерёдность; иначе корректные прогоны краснеют.
- **Дистрактор в реестре** — без py-tools «правильный выбор»
  невозможно провалить, а значит и доказать.
- **CLI-раннер вместо эндпоинта** — `/api/chat` уже отдаёт всю трассу;
  `POST /api/flow` добавил бы поверхность ради нуля новых возможностей.
- **Без системного промпта-навигатора** — выбор только по описаниям
  инструментов; deepseek-v4-flash справился без подсказок (это и есть
  находка дня). Отвергнуто: подсказка «используй подходящие
  инструменты» — замешивала бы steering в чистый тест маршрутизации.
- **Самодостаточная папка**: серверы скопированы из дней 18/19, а не
  импортируются по соседним путям — день остаётся замороженным
  снимком. Базы tracker/scheduler пересоздаются в `day20/data/`.
