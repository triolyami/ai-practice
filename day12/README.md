# Персонализация ассистента — день 12

Задание: добавить персонализацию поверх модели памяти: создать профиль
пользователя, описать предпочтения (стиль, формат, ограничения),
подключить профиль к каждому запросу. Проверить: ответы для разных
профилей, что ассистент учитывает автоматически. Результат:
персонализированный агент, адаптированный под пользователя.

База — день 11 (Agent + SQLite + слои памяти + пост-ходовой экстрактор).
**Убрано**: рабочая память и вся механика областей (workspaces-таблица,
`sessions.workspace_id`, `/api/working`, `/api/workspaces`, `/api/promote`,
`/api/workspace/delete`, группировка чатов). Вместо задачного слоя —
пользовательский: **профиль**.

## Профиль = файл, привязка = к чату

Профили — markdown-файлы `day12/profiles/<slug>.md`, по файлу на профиль.
Формат — тот же секционный, что у `longterm.md`, плюс необязательная
секция `## Пайплайн`:

```markdown
# Код-ревьюер
## Профиль
- обращение: на «ты»
## Стиль
- тон: прямой, без комплиментов
## Формат
- ответ: вывод первой строкой
## Ограничения
- не пиши код целиком
## Пайплайн              <- если есть, запрос превращается в цепочку шагов
- разбор: проанализируй запрос
- ответ: дай решение по разбору
- проверка: критически проверь свой ответ
```

- Привязка ручная, на чат (`sessions.profile_id`): чип «профиль: X ▾» в
  композере, «без профиля» — пустая привязка. Авто-роутера нет.
- Файл читается **с диска на каждый запрос** — правка (из UI или снаружи)
  видна со следующего ответа; удалённый файл деградирует честно: блок не
  уходит, в мете `profile_missing`.
- Лимиты: ≤30 строк на секцию, ≤200 символов на значение, ≤20 КБ файл,
  ≤8 шагов пайплайна.

## Три персонализации + два слоя памяти

```
запрос = [system: личность агента]
       + [system: ПРОФИЛЬ ПОЛЬЗОВАТЕЛЯ «имя» — заявленные предпочтения]  layers.profile
       + [system: ДОЛГОСРОЧНАЯ ПАМЯТЬ — выученное о пользователе]        layers.longterm
       + вся история диалога (MAX_TURNS)                                layers.short
       + [user: новое сообщение]
```

| слой | область | хранилище | кто пишет |
|---|---|---|---|
| краткосрочная | этот чат | таблица `messages` | автоматически |
| профиль | пользователь заявляет | файлы `profiles/*.md` | пользователь (UI или редактор) |
| долговременная | пользователь, навсегда | файл `memory/longterm.md` | LLM-экстрактор |

- **Заявленное** (профиль) и **выученное** (longterm) разведены
  специально: экстрактор получает текст активного профиля и обязан не
  дублировать то, что в нём уже заявлено; `drop_declared()` дополнительно
  режет строки, чей ключ совпадает с ключом из профиля.
- **Поведенческая** персонализация — `## Пайплайн`: запрос выполняется
  шагами, по одному вызову модели на шаг; каждый шаг получает общий префикс
  (личность + профиль + долговременная) + свою инструкцию как
  system-сообщение + исходный вопрос с результатами предыдущих шагов
  (история диалога — только у первого шага). События `step_start` /
  `delta` (с полем `step`) / `step_done`; в транскрипт пишется только
  `user + финальный ответ` — и только если дошли до конца: падение
  середины пайплайна не оставляет полуход.
- **Тумблеры** `layers {short, profile, longterm}` — привязанный профиль
  с выключенным слоем в запрос не уходит (быстрый A/B внутри чата);
  `meta.profile` / `meta.pipeline` / `meta.tokens.profile` фиксируют, что
  именно применилось.

## Файлы

- **`profiles.py`** — файловое хранилище: `list_profiles()`,
  `read_profile(slug)` (парсит при каждом чтении — кеша нет),
  `write_profile`, `delete_profile`, `slugify(name)`; `parse_profile()` —
  обобщённый парсер секций, `## Пайплайн` → упорядоченные шаги.
- **`agent.py`** — `profile_id` + `configure(profile=…)`; `_request()`
  вставляет профиль-блок после персоны; `send_stream` выбирает
  `_run_single` / `_run_pipeline`; `covered` — курсор экстрактора на
  сессию; снапшот/восстановление с `profile_id`.
- **`memory.py`** — экстрактор ужат до одного блока `ДОЛГОСРОЧНОЕ:`
  (ЦЕЛЬ/ПЛАН/ФАКТЫ умерли вместе с рабочей памятью), в промпт добавлен
  активный профиль + правило «заявленное не дублировать», фильтр
  `drop_declared()`.
- **`storage.py`** — `sessions.profile_id` + `sessions.covered`; таблицы
  `workspaces` больше нет.
- **`server.py`** — порт **7871**; `config.profile` (slug/пусто,
  `config.workspace` → 400 с подсказкой); `GET /api/profiles`,
  `GET /api/profile?id=`, `PUT /api/profile {id?,name,content}`,
  `POST /api/profile/delete`; NDJSON: `start.meta.profile` +
  `step_*`-события на пайплайнах. Глобальный BUSY → 409 (пайплайн — один
  ход, общие файлы — общая сериализация).
- **`tokens.py`** — `breakdown()`: system / longterm / **profile** /
  history / request.

## Сценарий «ответы для разных профилей» (прогоняется вручную)

1. Заведите два чата: к одному привяжите `lakonichny`, к другому —
   `mentor`; задайте обоим один вопрос — сравните стиль, формат и мету
   (`профиль «…»` под ответом).
2. Привяжите `reviewer` и попросите разобрать идею: ответ придёт
   пайплайном — три фазы над финальным ответом, в мете
   `пайплайн: разбор → ответ → проверка`.
3. В чате с профилем снимите чекбокс «профиль» в настройках — ответ без
   профиля при той же привязке; верните — профиль снова в запросе.
4. Скажите что-то уже заявленное в профиле («отвечай списком» при
   `lakonichny`) — в `longterm.md` это не запишется; скажите новый факт
   о себе — запишется и будет виден во всех чатах.
5. Отредактируйте профиль в панели справа (или файл руками) — следующий
   ответ того же чата уже по новой версии; удалите файл — чат продолжит
   без профиля, мета скажет «не найден».

Выводы сознательно не вшиты — прогон и наблюдения за вами.

## Принятые решения (и что отвергнуто)

- **Профиль — файл, не строка в БД**: куратор прямо предложил «побить на
  файлы»; листинг каталога и есть список профилей; правится любым
  редактором, переживает удаление базы. Отвергнуто: таблица `profiles`
  (прячет сущность, которую курс хочет видеть) и один глобальный активный
  профиль (не даёт A/B двух чатов рядом).
- **Пайплайн — секция внутри профиля**, а не отдельная библиотека скиллов:
  профиль — это «как со мной работать», и «на такой запрос спавнись такие
  агенты» — часть этого описания. Одна секция, ≤8 шагов, шаги —
  «имя: инструкция». Отвергнуто: промпт «сначала X потом Y» одним вызовом
  (это промпт-инжиниринг, а не оркестрация) и каталог `skills/*.md`
  (удвоил бы поверхность без выигрыша для задания).
- **Рабочая память удалена целиком**, а не оставлена спящей: области
  существовали только чтобы делить карточку задачи между чатами; без
  рабочей памяти это мёртвая концепция — половина `storage.py`, группировка
  сайдбара и четыре эндпоинта. Курсор `covered` переехал в колонку
  `sessions` (карта по областям была нужна, пока чаты делили один курсор).
- **Профиль — отдельный system-блок после персоны**, не слитие в промпт
  агента: сохраняет тумблер слоя, сегмент токенов и происхождение; при
  конфликте с персоной поздняя инструкция важнее — это задокументировано.
- **Привязка ручная, на чат**: авто-роутер профилей отвергнут (выбор
  профиля — осознанное действие пользователя; «профиль под задачу»
  естественно ложится на чат).
- **Пайплайн делит BUSY с обычными ходами**: n вызовов подряд под общим
  локом — осознанная цена за простоту одиночного демо; в транскрипт идёт
  только `user + финал`, промежуточные выводы живут в NDJSON-событиях и
  мете хода.
