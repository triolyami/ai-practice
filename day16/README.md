# MCP-инструменты — день 16

Задание:

> Установите MCP SDK / клиент (или поднимите MCP-сервер, если используете
> локальный вариант). Сделайте минимальный код, который: устанавливает
> MCP-соединение; получает от MCP список доступных инструментов.
> Проверьте: соединение устанавливается; список инструментов корректно
> возвращается. Результат: код, который подключается к MCP и выводит
> список доступных инструментов.

Оцениваемое ядро маленькое — **подключиться, получить список
инструментов, вывести его**. Поэтому оно живёт не только внутри
приложения, но и отдельным скриптом `mcp_probe.py` (см. ниже). Ось
сравнения этого дня: **язык и транспорт MCP-сервера для клиента —
донт-кейр** — один и тот же `Client.list_tools()` возвращает одинаковые
формы от Python-сервера и TypeScript-сервера. Чтобы это показать, в
реестр подключены оба.

База — день 14 (Agent + реестр сессий + SQLite + busy-lock + React).
**Убрано**: инварианты целиком (`invariants.py`, `invariants/`,
`/api/invariant*`, `config.invariant`/`config.enforce`, линт/ретрай,
весь инвариант-UI, колонки `sessions.invariant_id`/`enforce`).
Осталось чистое ядро: чат + токен-учёт.

**Не-цель**: модель не видит и не вызывает инструменты — в запросе нет
`tools`/`tool_calls`, вывод инструментов не попадает ни в историю, ни в
токен-учёт. Тулколлинг — область следующего дня.

## Архитектура

```
server.py (синхронный ThreadingHTTPServer)
   │  GET /api/mcp        → hub.servers()      (кэш статусов и инструментов)
   │  POST /api/mcp/call  → hub.call_tool(...) (run_coroutine_threadsafe)
   ▼
mcp_hub.py — daemon-поток владеет asyncio-циклом;
   AsyncExitStack держит по одному живому mcp.Client на запись
   реестра. Сбой записи → строка status="error"; чат и соседние
   серверы не затрагиваются.
   │
   ├─ py-tools  stdio  sys.executable day16/tools_server.py   (mcp v2, Python)
   └─ ts-tools  stdio  node ts-tools/node_modules/tsx/dist/cli.mjs server.ts
                                                              (@modelcontextprotocol/sdk 1.30.0)
```

Почему поток + цикл, а не `asyncio.run()` на запрос: `asyncio.run`
каждый раз порождал бы stdio-подпроцесс и заново делал handshake.
Держать подключения дешевле и правильнее — к тому же статус сервера
(протокол, server_info, инструменты) кэшируется при старте и отдаётся
`/api/mcp` мгновенно.

Реестр — `MCP_SERVERS` в `config.py`: `{id, transport, command|args|env|
cwd | url}`. `transport: "stdio"` порождает подпроцесс,
`transport: "http"` — Streamable HTTP по URL (для будущих удалённых
серверов). Неизвестный транспорт → честная строка `error`, а не падение.

## Два демо-сервера

Оба отдают одинаковый набор из пяти инструментов — `server_time`,
`add`, `echo`, `notes_list`, `notes_add` — с русскими описаниями.
Различаются детали реализации (у Python-сервера схемы с `title`, у
TS — `$schema` draft-07; `add` возвращает `"5.0"` у Python и `"5"` у
TS), но форма списка идентична — это и есть демонстрация интеропа.
Договорённая версия протокола тоже разная: py-tools → `2026-07-28`,
ts-tools → `2025-11-25`.

Stdio-серверы **ничего не пишут в stdout** — он зарезервирован под
JSON-RPC; диагностика только в stderr.

## Файлы

- **`config.py`** — `MCP_SERVERS` (реестр), порты/модели как в дне 14.
- **`mcp_hub.py`** — `MCPHub(registry, client_factory=...)`: `start()`,
  `servers()`, `tools(server)`, `call_tool(server, name, args)`.
  `client_factory` — точка для офлайн-проверок (in-process клиент).
- **`tools_server.py`** — Python `MCPServer`, пять инструментов, stdio.
- **`ts-tools/`** — `package.json` (`@modelcontextprotocol/sdk@1.30.0`,
  `tsx@4.23.13`), `server.ts` — зеркало инструментов.
- **`mcp_probe.py`** — standalone-CLI, буквальный результат задания:
  коннектится ко всем записям реестра и печатает server_info, протокол
  и таблицу инструментов (имя / описание / input_schema). Веб-приложение
  для этого не нужно.
- **`server.py`** — порт **7873**; `GET /api/mcp` →
  `{servers: [{id, transport, status, server_info, protocol_version,
  error, tools[]}]}`; `POST /api/mcp/call {server, tool, arguments}` →
  `{content[], structured_content, is_error}`. Ошибки: неизвестный
  сервер → 404, неизвестный инструмент → 400, сбой инструмента →
  `is_error: true` в контенте (сессия не рвётся). Лог старта печатает
  по каждой записи: результат коннекта, протокол, число инструментов.

## Фронтенд

Копия дня 14 без инвариант-UI (dev-порт **5185**, прокси → 7873,
localStorage `day16-*-v1`, `dist/` закоммичен). В правой панели под
картой контекста — **«mcp-инструменты»**: по каждому серверу точка
статуса, имя/id, транспорт, версия протокола, текст ошибки; инструменты
сгруппированы по серверам, у каждого — описание и раскрываемый
`input_schema`. Кнопка «вызвать» раскрывает форму, сгенерированную из
схемы (string → текст, number → число, boolean → чекбокс, прочее →
JSON); результат или `is_error` рисуется под инструментом.

## Запуск

```bash
pip install -r requirements.txt                 # mcp>=2.2,<3
cd day16/ts-tools && npm install && cd ../..    # нужно только для ts-tools

# если в шелле стоит all_proxy=socks5h://… — снимите его: httpx без socksio
# падает («Using SOCKS proxy, but 'socksio' is not installed»)
env -u all_proxy -u ALL_PROXY .venv/bin/python day16/server.py  # http://127.0.0.1:7873

cd day16/frontend && npm run dev    # dev-режим: http://localhost:5185
```

**Без Node**: если `day16/ts-tools/node_modules` не установлен, запись
`ts-tools` просто показывает строку `error` в `/api/mcp` и в панели —
py-tools и чат работают как обычно.

**Standalone-пробник** (не нужен ни веб, ни фронт):

```bash
.venv/bin/python day16/mcp_probe.py
```

## Проверено

- `day16/offline_check.py` — без сети и node: состав запроса, мета и
  тоталы, отключение истории, сбой модели, снапшоты, форма breakdown,
  legacy-подсказки конфига, и in-process `Client(MCPServer)` через хаб:
  коннект/список/вызовы, `is_error` на битых аргументах, KeyError/
  LookupError для неизвестных server/tool, запись с неизвестным
  транспортом деградирует в `error` и не роняет соседнюю.
- Живой прогон: старт на 7873, в логе `mcp[py-tools]` / `mcp[ts-tools]`
  с протоколами и числом инструментов; `GET /api/mcp` — оба сервера
  `ok`; `add` на каждом; битые вызовы → ожидаемые формы ошибок; ход
  чата — мета с токенами без изменений, в запросе нет полей tools.
- `mcp_probe.py` — печатает оба сервера и по 5 инструментов с описаниями
  и схемами.

## Принятые решения (и что отвергнуто)

- **Держать подключения в daemon-потоке с asyncio-циклом**, а не
  `asyncio.run()` на запрос: иначе каждый вызов перезапускал бы
  stdio-сервер; плюс кэш инструментов нужен `/api/mcp` мгновенно.
  Отвергнуто: поднимать клиента лениво при первом вызове — стартовый
  лог «кто подключился» и честные error-строки требуют коннекта при
  старте.
- **Реестр в `config.py`, спеки декларативные** (`{id, transport,
  command|url}`): добавление сервера — одна запись, без кода. Фабрика
  `make_client(spec)` оставлена точкой расширения — офлайн-проверки
  подменяют её in-process клиентом.
- **Свои два сервера вместо одного внешнего**: задача просит «установить
  соединение и получить список» — пара идентичных по форме серверов на
  разных языках/SDK доказывает интероп сильнее, чем любой один.
- **Инструменты — детерминированные и крошечные** (время, арифметика,
  эхо, in-memory заметки): список и вызовы воспроизводимы и проверяемы
  без магии; `notes_*` показывают, что у сервера может быть своё
  состояние, независимое от чата.
- **Никаких инструментов в LLM-запросе**: задание про соединение и
  дискавери, а не тулколлинг. Панель «вызвать» — ручная проверка, что
  список настоящий; вывод в историю и токены не попадает.
- **Ошибка записи — данные, не исключение**: сломанный сервер виден в
  UI и API как строка `status:"error"`; чат работает всегда.
- **`structured_content` проксируется как есть**: Python SDK возвращает
  его для типизированных тулов; TS — `null`. Разница видна прямо в
  ответах API — лишний повод посравнивать реализации.
