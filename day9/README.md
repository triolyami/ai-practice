# Управление контекстом: сжатие истории — день 9

Задание: реализовать механизм управления контекстом — хранить последние N
сообщений «как есть», остальное заменять summary (например, каждые 10
сообщений), хранить summary отдельно и подставлять его в запрос вместо
полной истории. Сравнение качества и расхода токенов до/после выполняется
вручную — день 9 делает такое сравнение возможным: три режима в одном
диалоге, раздельные счётчики и карта контекста.

## Что изменилось со дня 7

День 7 научил агента помнить (SQLite-персистентность), день 8 — считать
(токены и стоимость). День 9 решает их общий конфликт: история в запросе
растёт с каждым ходом, а полный транскрипт пересылать дорого. Теперь агент
хранит историю **целиком** (ничего не удаляется), но в запрос модель уходит
не она, а её сжатая замена:

```
запрос = [system] + [сводка] + последние 10 сообщений как есть + [новый вопрос]
                    └── сводка хранится отдельно, вне истории
```

- **`compressor.py`** (новый) — вся механика сжатия: `compress()` собирает
  из старой сводки и очередного фрагмента промпт, вызывает ту же модель
  (non-stream, temperature 0) и возвращает обновлённый текст + usage;
  `render_rolling_message()` / `render_chunks_message()` превращают сводку
  в системное сообщение для запроса.
- **`agent.py`** — три режима сжатия (`compression`):
  - `off` — как в днях 7–8: полная история в каждом запросе (базовая линия
    для сравнения);
  - `rolling` (по умолчанию) — одна скользящая сводка: каждые 10 сообщений
    сверх окна она обновляется вызовом «старая сводка + новый фрагмент →
    новая сводка»; расход на сводку не растёт с длиной диалога;
  - `chunks` — независимая сводка на каждые 10 старых сообщений; в запрос
    уходит один объединённый системный текст «по периодам».
  У каждого режима своя ячейка состояния (`comp_state`) и свой указатель
  покрытия `covered` (сколько сообщений от начала истории уже сжато), поэтому
  режимы можно переключать в любой момент: отставший режим «догоняет» бэклог
  чанками по 10 после следующего ответа. Триггер сжатия: после каждого
  ответа, пока непокрытых сообщений сверх окна 10 накопилось ≥ 10.
  Событие сжатия — не-blocker: если вызов summary упал, в чат уходит
  `notice`, состояние не меняется, попытка повторится после следующего хода.
- **`tokens.py`** — `breakdown()` получил отдельный бакет `summary`
  (оценка токенов сводки в запросе); из дня 8 не переехали `fits`/
  `trim_to_fit` — переполнение теперь не резать, а предупреждать заранее.
- **`storage.py`** — в `sessions` три новых поля: `compression` (текущий
  режим), `comp_state` (JSON: текст/чанки сводок + covered), `stats`
  (JSON: totals и token_log). Таблица `messages` не изменилась — транскрипт
  по-прежнему хранится целиком.
- **`server.py`** — порт 7868; `parse_config` принимает `compression`;
  сохранение в базу происходит после `done` (сжатие идёт уже после него —
  save выполняется и когда ход завершился событиями `summary`). `GET /api/agent`
  отдаёт сводки и `context_preview`.

## Метаданные и карта контекста

- каждый ход в `meta` несёт `mode`/`mode_label`, `summarized` (сколько
  сообщений уже подменено сводкой) и разбивку `tokens` на
  система/сводка/история/запрос; все итоги — факт из usage API:
  `total_actual` (промпт последнего запроса) и `total_with_answer`
  (промпт + текст ответа без скрытых рассуждений — столько займёт
  следующий запрос, так же «контекст» считают codex/opencode; у
  thinking-моделей API-счётчик ответа включает рассуждения, которые в
  контекст не возвращаются — они вычтены по `reasoning_tokens` или
  оценке). «Контекст» в панели токенов и проценты — из
  `total_with_answer`, итоги строк карты контекста — из `total_actual`;
  эвристическая оценка осталась для «следующего запроса» (его ещё не
  отправляли) и как фолбэк, если API не вернул usage;
- `totals` считает промпт/ответ/стоимость **отдельно по каждому режиму**
  плюс отдельный бакет `summary_calls` — накладные расходы на само сжатие;
- `context_preview` (в `describe()`, `done` и `summary`-событиях) — оценка
  состава следующего запроса: на ней построена «карта контекста» справа
  сверху: полоса следующего запроса + по полосе на каждый прошлый ход
  (система/сводка/последние сообщения/запрос, ширина ∝ токенам). В режиме
  `off` зелёная полоса истории растёт без ограничений, в `rolling`/`chunks`
  вместо неё растёт синяя полоса сводки — сжатие видно глазами.

## Как сравнивать

1. Задайте 10–15 вопросов, чтобы накопилась история (кнопки «+10К/+50К» в
   композере ускоряют рост контекста).
2. Разверните «агент» в композере и переключайте «Сжатие истории»:
   без сжатия → скользящее → по чанкам.
3. Сравнивайте по одному диалогу:
   - «расход по режимам» в панели токенов — промпт/ответ/доллары на режим
     и накладные расходы вызовов `summary`;
   - карта контекста — как менялся состав запроса по ходам;
   - ответы — помнит ли агент факты из «сжатой» зоны (имена, цифры,
     договорённости из первых сообщений).
4. Сводку, которую реально видит модель, можно раскрыть в блоке «что помнит
   агент» справа.

## Запуск

Фронтенд собран и закоммичен в `day9/frontend/dist/`, поэтому Node не нужен:

```bash
cp .env.example .env   # вписать GLM_API_KEY и/или DEEPSEEK_API_KEY
.venv/bin/python day9/server.py
```

Открыть <http://127.0.0.1:7868>. Офлайн-проверка механики сжатия (без сети,
на фейковом клиенте): `.venv/bin/python day9/offline_check.py`.

## Пересборка фронтенда

```bash
cd day9/frontend
npm install        # один раз
npm run build      # dist/ для сервера
npm run dev        # режим разработки: :5180, прокси /api → :7868
```
